# SlideForge AI Consulting Product Strategy Plan

## Objective

Turn the current SlideForge AI codebase into a real-world consultant workflow platform for PowerPoint management, review, evidence grounding, and controlled agentic assistance, while keeping laptop-first deployment practical for Apple and Windows devices with a 16 GB memory constraint.

## Current State Assessment

### Product Architecture

- Frontend is a Vite + React single-page application with two major flows: upload and dashboard.
- Backend is a FastAPI application centered in `backend/app/main.py` with in-memory session orchestration and local file persistence.
- Core analysis pipeline already exists:
  1. session creation
  2. deck upload
  3. PPTX/PDF ingestion and preview generation
  4. parallel agent analysis
  5. language analysis and source grounding
  6. scorecard/deep-analysis generation
  7. annotated download and delivery packaging
- Storage is local-first:
  - session artifacts in `~/.slideforge/data`
  - ChromaDB for source grounding
  - SQLite for adaptation loop
  - CSV audit logs

### Implemented Features

- Deck upload for `PPTX` and `PDF`
- Session history restore by document fingerprint
- Per-slide scorecards, overlays, consultant summary, reliability and visual coverage
- Multi-agent analysis covering claims, structure, data lineage, visuals, framework detection, so-what, benchmarking, and slide context
- Issue panel with accept/dismiss actions
- Guardrail signing, template save/activate, and diff view
- Audit log view
- Delivery workflow with senior sign-off and package generation
- Local/cloud LLM provider switching (`api`, `mlx`, `ollama`, `lm_studio`, `transformers`)
- Source document upload for claim grounding and Excel upload for chart lineage, but these are backend-heavy and underexposed in the UI

### Key Gaps

1. `backend/app/main.py` is too monolithic for reliable product growth.
2. Several strong backend capabilities are not surfaced as primary workflows:
   - source document upload
   - Excel upload
   - revision loop
   - adaptation suggestions
   - diagnostics
3. The current product is mostly a deck evaluator, not yet a day-to-day consulting workspace.
4. The role model is trust-based only; acceptable for a local pilot, but not for enterprise rollout.
5. Annotated download is PPTX-centric; PDF workflow is weaker for downstream editing.
6. Template discovery is useful but still POC-like and shallow.
7. Vision fallback quality depends heavily on LM Studio availability.

## Guardrail Assessment

### Is the guardrail involved?

Yes. Guardrails are involved in the current system, but their integration is uneven.

### Where guardrails are actively used

- `rubric_weights` and `pass_threshold` directly affect final scoring and pass/fail summary.
- `playbook_rules` are injected into the Insight Extractor prompt, so client rules can influence claim review.
- `language_rules` are used in the visual analysis flow for text-density thresholds.
- `language_rules.prohibited_phrases` are enforced in language analysis as hard blocks.
- `discovered_patterns.visual` is used by visual checks, such as footer expectations.
- guardrail context is included in deeper slide-review prompts and in session guardrail application, signing, templates, and delivery governance.

### Where guardrails are only partially used or weakly enforced

- several analysis agents accept `guardrail` as an argument but do not materially use it in their logic
- framework, so-what, and benchmarking agents currently do not appear to enforce client-specific guardrail content beyond generic analysis
- many derived language rules from template discovery are created but not strongly enforced in runtime checks
- content-oriented rules are not yet consistently translated into deterministic checks or targeted scoring penalties

## Content Guardrail Quality Assessment

### Are the content guardrails perfect?

No. They are directionally good, but they are not perfect and not fully integrated.

### What is already working

- prohibited phrase enforcement exists
- claim-review prompts can see playbook rules
- so-what, framework, benchmarking, and slide-context analysis exist as separate quality layers
- guardrail templates, signing, and activation workflows are present

### What is missing for "perfect" content guardrails

1. discovered content rules are not consistently converted into runtime enforcement
2. many content rules remain prompt-level guidance instead of explicit checks
3. template-discovered language rules such as `one_key_message_per_slide`, `insight_led_headlines`, `avoid_prose_paragraphs`, and `expand_acronyms` are not comprehensively enforced
4. content agents are still more generic consulting reviewers than client-specific guardrail executors
5. there is no strong coverage model showing which guardrail rules were checked, passed, skipped, or failed per slide
6. guardrail diffing is narrower than the full schema and does not fully support content-rule change management

### Recommendation

Treat guardrails as a strong foundation, not a finished compliance system. The next product iteration should make content guardrails explicit, measurable, and traceable by:

- mapping every important content rule to a concrete runtime check or score dimension
- adding per-slide guardrail coverage reporting
- separating generic consulting QA from client-specific guardrail enforcement
- promoting discovered language and content rules into first-class validation logic

## What We Can Do Better

### 1. Move from analysis output to consultant outcomes

The product should not stop at "what is wrong with the slide." It should help consultants finish the task faster.

Enhancements:
- convert issues into clear actions: fix, defer, escalate, or accept risk
- show effort and impact for each issue
- provide deck-level action plans such as `fix these 3 slides first before partner review`
- generate a review summary suitable for manager or partner handoff

### 2. Make the system evidence-first

Today, evidence support exists, but it should become the center of trust.

Enhancements:
- require optional-but-prominent evidence upload during intake
- show evidence confidence by slide and by claim
- add `missing evidence` and `evidence stale` states
- allow source linking directly from issue cards and slide highlights
- create an evidence readiness score separate from design and language quality

### 3. Build a better editing loop

Today, the product is stronger at diagnosis than execution.

Enhancements:
- before/after rewrite previews for each suggested change
- grouped fix application by category: grammar, storyline, headline, citations
- slide snapshots before every accepted mutation
- one-click revert per fix, per slide, and per session
- a `recommended fix sequence` so consultants know what to apply first

### 4. Add deck-level intelligence

The current experience is slide-centric. Consulting quality is often deck-centric.

Enhancements:
- narrative map across all slides
- duplicate insight detection across deck
- inconsistent number and metric tracking across slides
- title and takeaway consistency checker
- appendix relevance and executive-summary alignment checks
- identify missing bridge slides between diagnosis and recommendation

### 5. Add operating-system style consultant workflows

The product can become much more useful if it supports recurring consulting tasks, not only QA.

Enhancements:
- `build executive summary from deck`
- `create steering committee pack`
- `prepare client-ready version`
- `generate appendix from evidence bundle`
- `compare v1 vs v2 deck`
- `extract actions, risks, and asks from deck`

### 6. Improve trust and explainability

Consultants and partners will trust the system more if every judgment is explainable.

Enhancements:
- per-issue reason trace: rule, evidence, model, confidence, fallback mode
- show whether a judgment came from deterministic logic, OCR, vision, or LLM inference
- show skipped checks explicitly
- introduce `low-confidence review needed` flags when the system is uncertain

### 7. Introduce quality modes

Different moments in consulting work require different strictness.

Enhancements:
- `Draft Mode`: more suggestions, fewer hard blocks
- `Manager Review Mode`: stronger storyline and evidence checks
- `Client Delivery Mode`: strict guardrails, sign-off gates, and packaging rules
- `Rapid Readout Mode`: optimized for fast meeting-pack cleanup

### 8. Make laptop deployment more resilient

For consultant adoption, the system must degrade gracefully on weaker machines.

Enhancements:
- hardware capability detection at startup
- auto-select runtime profile based on CPU, RAM, GPU, and platform
- background model warmup and health checks
- explicit fallback tiers for OCR, vision, grammar, and LLM functions
- a performance dashboard showing why a slower fallback path was used

### 9. Strengthen the grammar and language subsystem

Grammar is present, but it can be upgraded from a check layer into a full language-quality system.

Enhancements:
- distinguish grammar, punctuation, capitalization, register, and headline style separately
- add consulting-specific language checks such as parallelism, over-hedging, acronym expansion, and title directness
- make punctuation consistency a tracked score dimension
- show whether LanguageTool or regex fallback was used at issue level, not only globally
- allow guardrail-driven language profiles by client or engagement type

### 10. Make templates and guardrails much stronger

Guardrails should evolve into a real consulting policy engine.

Enhancements:
- rule coverage matrix by slide
- guardrail test harness with golden slides
- stronger diffing across full schema, not only confirmed rules
- rule severity tuning and environment-specific overrides
- client-specific packs combining layout, language, evidence, and delivery rules
- guardrail simulation mode before full activation

## What Excellent Looks Like

The mature version of this product should behave like this:

- a consultant uploads a deck and supporting materials
- the system identifies what is missing before analysis starts
- review results are grouped by business priority, not only by technical category
- every critical issue is traceable to a rule and, where relevant, to evidence
- suggested fixes are easy to review, apply, and revert
- the deck can be taken from rough draft to client-ready package inside one governed workflow
- the UI stays simple for consultants while still giving senior reviewers deep control when needed

## UI/UX Assessment

### Current Usability Verdict

The UI is visually strong and feature-rich, but it is not yet easy enough for day-to-day consultant use. It currently feels more like an analysis showcase than a guided consulting workflow tool.

### Main UX Problems

#### 1. First-time clarity is weak
- onboarding uses internal and technical language too early
- the upload screen exposes LLM and provider settings before the core task begins
- role selection is framed as system access rather than the user's job to be done

#### 2. The dashboard is too dense
- the evaluation screen surfaces too many concepts at once: scores, reliability, framework detection, so-what, benchmark validation, deep analysis, visual evidence, grammar, and council discussion
- consultants need a guided triage flow first and analytics second

#### 3. The workflow is not task-first
- issue review is separated from slide navigation
- the product does not yet clearly guide the user through "what should I fix next"
- core backend features such as evidence upload and Excel lineage are missing from the main consultant flow

#### 4. Terminology is too internal
- labels such as "Council of Agents", "Discovery", "Q-Loop", and "Inference Stack" increase cognitive load
- consultant-facing labels should focus on review, fixes, evidence, and delivery

#### 5. Role separation is incomplete
- consultant users still see senior governance concepts and are then told that they cannot complete them
- this creates friction and weakens confidence

#### 6. Accessibility and operability need work
- too much tiny text
- too many hover-dependent interactions
- some controls rely too heavily on color and compact badges
- action menus should work better for keyboard and touch use, especially during time-sensitive review sessions

### UX Direction

The product should feel like a consultant workbench with a simple primary loop:

1. Upload deck and evidence
2. See top issues and missing inputs
3. Jump to affected slide
4. Review suggested fix
5. Approve, dismiss, or defer
6. Export annotated or final client-ready package

### UX Recommendations

#### Consultant Mode
- make consultant mode the default day-to-day experience
- the default view should be an issue-resolution workspace, not a metrics wall
- show progress such as `12 issues remaining`, `3 critical`, `5 ready-to-apply`

#### Information Architecture
- create a clearer primary navigation:
  - Review
  - Evidence
  - Fixes
  - Rules
  - Delivery
- move advanced diagnostics and engine settings under an `Advanced` area

#### Plain-Language Labels
- rename `Council of Agents` -> `Review Comments`
- rename `Discovery` -> `Create Rules`
- rename `Prepare for Delivery` -> `Finalize Client Package`
- rename `Deep Analysis` -> `Detailed Review`

#### Guided Issue Resolution
- clicking an issue should take the user directly to the relevant slide and highlighted area
- add `Next issue`, `Previous issue`, and `Mark as reviewed`
- organize issues by lanes:
  - critical evidence/compliance
  - message/storyline
  - language/layout

#### Better Onboarding
- simplify the upload page copy
- keep one main call to action: `Upload deck`
- add a secondary call to action: `Add supporting files`
- collapse provider settings by default behind `Advanced settings`

#### Role-Specific UX
- consultant view: review, resolve, and download the annotated deck
- senior view: all consultant features plus rule approval, sign-off, delivery packaging, and system metrics
- avoid showing blocked actions when they are not relevant to the current role

#### Accessibility Baseline
- increase default text sizes for dense panels
- replace hover-only dismiss interactions with explicit menus or dialogs
- ensure that close buttons and controls are labeled clearly
- use icons plus text, not color alone, for status communication

## UX-Specific Feature Priorities

## Strategic Product Direction

### Product Positioning

Evolve from "agentic consulting deck evaluator" into "consulting presentation operating system" with four pillars:

1. Intake and understanding
2. Review and QA
3. Evidence and compliance
4. Controlled editing and delivery

### Recommended Product Surface

#### Workstream 1 - Consultant Workspace

Add a persistent engagement workspace instead of a single-session upload tool.

Features:
- Engagement home with client, workstream, meeting, due date, owner, status
- Asset panel for deck, Excel, PDF, Word, notes, transcript, brand playbook
- Task queue for common consultant jobs
- Recent actions timeline and open issues

Why:
- This matches how consulting teams actually manage deck work across multiple supporting files.

#### Workstream 2 - Source-Aware Deck Review

Promote evidence grounding and lineage from optional backend capability to first-class workflow.

Features:
- Upload supporting documents before analysis
- Explicit evidence coverage view per slide
- "Unsupported claim" lane with source links
- chart/table lineage panel showing source sheet and mismatch details
- completeness flag when a slide has claims but no supporting source set

Why:
- This is one of the strongest differentiators already latent in the backend.

#### Workstream 3 - Real Editing Copilot

Move from passive issue review into controlled remediation.

Features:
- one-click safe rewrites for grammar, headline strengthening, so-what sharpening
- assistant-generated alternative headlines and executive summaries
- structured revise loop in UI with before/after diff
- "apply to this slide" vs "apply across deck" controls
- undo stack and deck snapshot restore

Why:
- Real firms need draft improvement, not only scoring.

#### Workstream 4 - Guardrails and Delivery Governance

Strengthen the good foundation already present.

Features:
- client/team template library with version labels
- pre-delivery checklist with blocking gates
- delivery readiness report
- package manifest with signed audit metadata
- partner-ready approval mode

Why:
- This aligns with consulting QA and governance expectations.

## Agentic Workflow Design

### Recommended Multi-Agent Operating Model

Use specialized but bounded agents. Do not create an unconstrained autonomous swarm.

#### 1. Intake Agent
- classifies uploaded materials
- identifies deck, sources, playbooks, transcripts, and background docs
- recommends missing inputs before analysis starts

#### 2. Deck QA Orchestrator
- coordinates existing analysis agents
- produces deck-level and slide-level scorecards
- manages re-runs after edits

#### 3. Evidence Agent
- links claims to uploaded sources
- surfaces unsupported assertions
- traces chart/table values back to source documents

#### 4. Storyline Agent
- checks narrative arc, executive message, and recommendation flow
- proposes stronger headlines and section ordering

#### 5. Remediation Agent
- generates constrained rewrite suggestions
- applies safe text-level fixes only when explicitly approved
- never auto-mutates the deck without snapshotting and diffing

#### 6. Delivery Agent
- validates sign-off, audit completeness, metadata stripping, and export packaging

### User-Facing Workflow

1. Create engagement
2. Upload current deck
3. Upload evidence bundle and optional client playbook
4. Intake Agent identifies missing materials
5. Deck QA Orchestrator runs review
6. User triages issues in three lanes:
   - critical evidence/compliance
   - storyline/message
   - language/layout
7. Remediation Agent proposes fixes
8. User approves targeted updates
9. Delivery Agent performs final packaging and sign-off

### Operational Rules

- Human approval required for all edits to client-facing artifacts
- Every agent action should emit a structured audit event
- Every deck mutation must produce a reversible snapshot
- Agent tools should be restricted by role and artifact type
- Keep deterministic checks ahead of LLM judgment wherever possible

## OCR / Parsing Recommendation

### Current Baseline in Repo

- Existing stack already uses `pdfplumber` + `Surya` + native `python-pptx` extraction + optional multimodal vision.
- This is directionally correct for a laptop-first consulting product.

### Chandra OCR vs PDF-Extract-Kit vs Existing Surya-Centric Stack

#### Chandra OCR

Pros:
- strong end-to-end document-to-structured-output capability
- attractive for high-quality complex document parsing

Cons:
- too heavy for a typical offline consultant laptop with 16 GB RAM
- poor fit for CPU-only or low-VRAM Windows machines
- weak confidence for smooth Apple Silicon laptop deployment at this memory budget
- overkill for PPTX, where native structure extraction is better than OCR

Recommendation:
- do not use as the default local parser
- consider only as a cloud/offline-lab option later for high-complexity documents

#### PDF-Extract-Kit

Pros:
- modular and strong on complex PDFs, tables, formulas, academic layouts

Cons:
- operationally heavier than needed for consultant laptop workflows
- more engineering overhead than business value for slide decks
- AGPL licensing is a serious product/commercial constraint

Recommendation:
- do not adopt as the primary stack for this product
- only revisit if formula-heavy technical document extraction becomes a core market need

#### Surya-Centric Local Stack

Pros:
- already partially integrated
- much better laptop fit
- supports CPU/MPS/CUDA scenarios better than heavy single-model alternatives
- aligns with business slide/PDF use cases where layout detection and OCR are helpful, but native PPTX parsing remains primary

Cons:
- requires good fallback handling and model lifecycle management
- still needs a more robust local parsing profile and performance tuning

Recommendation:
- keep `Surya + pdfplumber + python-pptx` as the primary local path
- strengthen it rather than replacing it

### Practical Hardware Recommendation

#### Apple Silicon 16 GB
- supported path: native PPTX parsing + Surya/MPS when available + small local LLM or LM Studio remote/local
- avoid Chandra default deployment

#### Windows ThinkPad 16 GB without GPU
- supported path: native PPTX parsing + pdfplumber + CPU Surya fallback + cloud or lightweight local LLM
- avoid heavy OCR/vision models

#### Windows 16 GB with moderate GPU
- support Surya + LM Studio/Ollama vision if available
- still avoid Chandra as default

### OCR/Parsing Product Plan

1. Preserve native PPTX extraction as primary path
2. Use PDF OCR/layout only for PDFs and scanned artifacts
3. Create runtime profiles:
   - `Laptop Safe`
   - `Laptop Plus GPU`
   - `Cloud Enhanced`
4. Make parsing strategy explicit in settings and telemetry

## Self-Improvement / RL Recommendation

### Agent Lightning vs AutoResearch

#### AutoResearch

- Not suitable for SlideForge product workflows
- Designed for autonomous model-training/code experimentation
- Wrong abstraction for PowerPoint operations and consulting task management

Recommendation:
- do not integrate

#### Agent Lightning

- Potentially useful later as an internal optimization framework for agent trajectories
- Not suitable to embed inside the desktop runtime
- Requires controlled traces, reward design, offline replay, and rollback discipline

Recommendation:
- do not integrate into the shipping app now
- consider only as a future internal backend experimentation layer

### Recommended Improvement Strategy Instead of Embedded RL

Stage 1 - instrumentation
- capture tasks, tool calls, user accepts/dismisses, undo events, retries, runtimes, and deck diffs

Stage 2 - offline evaluation harness
- benchmark on real consulting tasks and golden decks

Stage 3 - prompt and policy optimization
- improve routing, prompts, thresholds, and tool selection without RL

Stage 4 - human-reviewed tuning
- use accepted edits and reviewer choices as supervised or preference data

Stage 5 - limited internal RL experimentation
- evaluate Agent Lightning only in a separate controlled training environment

## Success Metrics

### Product Metrics
- time from upload to actionable review
- percentage of unsupported claims caught before partner review

### Technical Metrics
- parse success rate by file type

## Final Recommendations

1. Keep the current local-first direction.
2. Double down on the existing Surya-centric stack instead of replacing it with Chandra or PDF-Extract-Kit.
3. Reposition the product from evaluator to consultant workflow platform.
4. Surface evidence upload, lineage, remediation, and engagement management as first-class workflows.
5. Avoid embedded self-improving RL in the desktop app.
6. Use eval-driven improvement first; consider Agent Lightning only later in a separate controlled backend experimentation loop.

## Suggested First Implementation Slice

Build the first release around this sequence:

1. Guided review home and issue-resolution dashboard
2. Source bundle upload wizard
3. Evidence coverage + Excel lineage UI
4. Revision/remediation center with before/after diff
5. Engagement workspace shell
6. Backend router refactor for maintainability

This path produces the highest business value with the lowest strategic risk while reusing the strongest assets already present in the codebase.
