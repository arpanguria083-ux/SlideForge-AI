## Background — What Was Wrong

The original `parallel_analysis.py` had **zero LLM calls** in any of the 4 agents.
Every result was produced by hardcoded rules, regex, and fixed scores.
This caused the same issue message to appear on every slide.

### Bug Summary (original code)

| Bug | Location | Impact |
|---|---|---|
| `list(range(len(headlines)))` — flags ALL slides | `_check_narrative_arc()` line 148 | Every slide got "Missing problem statement" |
| Score hardcoded to `85` | `run_insight_extractor()` | Score never reflects actual findings |
| Score hardcoded to `80` | `run_structure_auditor()` | Same |
| Score hardcoded to `50` | `run_data_lineage_agent()` when no Excel | Same |

| Text density = `char_count / (width * height * 500)` | `_calculate_text_density()` | Wrong formula — EMU not pixels |
| `LocalVisionModel` is default | `vision.py` | Returns a stub string — not actual analysis |

## What Was Fixed (Already Implemented)

The following are already in `parallel_analysis.py` as of March 2026.
These sections describe **what was done** — read before extending.

### FIX-01 — Insight Extractor now uses LLM

**Class:** `InsightExtractor`

The old extractor used 5 regex patterns to find numbers/percentages and flagged every match as a "claim". The new extractor:

- Sends each slide's text to the LLM with a structured prompt
- LLM classifies each claim as `SUPPORTED`, `UNVERIFIED`, or `UNSUPPORTED`
- Only `UNSUPPORTED` and `UNVERIFIED` claims create annotations
- `UNSUPPORTED` = hard block, `UNVERIFIED` = warning
- Score formula: `100 - (hard_blocks × 15) - (warnings × 5)`

**Key prompt structure:**
```
SLIDE TITLE: ...
SLIDE TEXT: ...
Return JSON array: [{claim, status, reason, suggestion}]
```

---

### FIX-02 — Structure Auditor now uses LLM (3 separate calls)

**Class:** `StructureAuditor`

The old auditor used keyword lists (`["challenge", "issue", "problem"]`) and flagged ALL slides when none matched. The new auditor makes three targeted LLM calls:

**Call 1 — Narrative arc (once per deck):**
- Sends the full deck outline (all titles numbered)
- LLM evaluates pyramid principle compliance
- Returns `{arc_valid, arc_type, issues: [{slide_index, message, suggestion}]}`
- Flags only specific slides, never all slides

**Call 2 — Headline quality (once per deck):**
- Checks each headline: action-oriented vs. descriptive
- Action-oriented = conveys a finding ("Revenue declined 23%")
- Descriptive = just labels the topic ("Revenue Analysis")
- Returns only weak headlines as `suggestion`-severity annotations

**Call 3 — MECE compliance (per slide, only if slide looks like a framework):**
- Triggered only when slide has 3+ bullet points or parallel structure markers (`1.`, `a)`, `First`, etc.)
- LLM checks for overlap and coverage gaps
- Returns `warning` if MECE violated

---

### FIX-03 — Data Lineage Agent — mismatch detail improved

**Class:** `DataLineageAgent`

The old agent returned a generic "Chart values do not match source Excel" with no specifics. The new agent:
- Uses `> 0.5%` threshold (matches PRD F3.3 spec exactly)
- Reports the specific cell and values that differ: `"Cell [2,1]: slide shows 45.3, Excel shows 44.1"`
- When no Excel is provided, marks charts as `suggestion` (not `50` score) — avoids penalising decks for a missing input file

### FIX-04 — Visual Analysis Agent uses Surya layout detection

**Class:** `VisualAnalysisAgent`

Replaces the broken text density formula with real image-based layout analysis.

#### Why Surya (not Chandra)

| | Chandra | Surya |
|---|---|---|
| Size | 9B params, CUDA required | ~300MB, CPU/MPS/CUDA |
| Purpose | OCR for scanned documents | Layout detection on images |
| Fit for PPTX | Wrong — text already in XML | Right — detects visual regions |
| Offline | Needs large GPU | Works on laptop CPU |

#### What Surya detects on slide images

Surya `LayoutPredictor` classifies 15+ block types per image:
`text`, `section-header`, `caption`, `footnote`, `table`, `figure`, `image`, `page-header`, `page-footer`, `list-group`, `equation-block`, `code-block`

Surya `OrderPredictor` assigns a reading sequence number to each detected block.

#### How VisualAnalysisAgent uses Surya

1. Loads the rasterized PNG of the slide (already generated by `convert_pptx_to_images`)
2. Runs `LayoutPredictor` → gets list of blocks with labels and pixel bounding boxes
3. Checks for `page-footer` block → flags if required by guardrail but missing
4. Computes real text density = `sum(text_block_areas) / slide_area` (pixel-accurate)
5. Runs `OrderPredictor` → checks if > 40% of blocks are out of sequence → flags reading order issue
6. Checks `figure/image/table` ratio → flags if slide is 100% text with no visuals

**Fallback (no Surya):** Uses EMU bounding boxes from python-pptx text boxes to approximate density and footer position. Same annotation schema.

```
### EXT-03 — Claim–Evidence ChromaDB Integration in Insight Extractor

**File:** `backend/app/agents/parallel_analysis.py` → `InsightExtractor`
**File:** `backend/app/services/claim_evidence.py`
**Current state:** `InsightExtractor` asks the LLM to classify claims but does NOT query ChromaDB to check if evidence exists in source documents. The PRD (F3.1, F5) requires a two-step process: LLM extracts claims → ChromaDB checks grounding.

#### What to build

After the LLM identifies `UNVERIFIED` claims, run a ChromaDB retrieval step:
- Query the session's ChromaDB namespace with the claim text
- If retrieval returns a chunk with cosine similarity ≥ 0.80, run an entailment check: does the chunk actually support the claim?
- If entailment passes: downgrade to `SUPPORTED` (remove annotation)
- If entailment fails: upgrade to `UNSUPPORTED` (hard block) — evidence exists but contradicts the claim
- Log the claim + retrieved chunk + entailment result to SQLite for adaptation loop

This requires the `InsightExtractor` to receive the session's `client_namespace` and a `ChromaDBManager` instance.
```

```python
class ChromaDBManager:
    def query_documents(self, namespace: str, query: str, n_results: int = 3) -> list[dict]:
        # returns list of {"document": str, "distance": float, "id": str}
        collection = self.get_collection(namespace)
        if not collection:
            return []
        results = collection.query(query_texts=[query], n_results=n_results)
        docs = results["documents"][0]
        dists = results["distances"][0]
        return [{"document": d, "distance": dist} for d, dist in zip(docs, dists)]
```


Returns one of: "SUPPORTED", "UNVERIFIED", "UNSUPPORTED", "NO_RAG" (when no docs in namespace)

Logic:
1. results = chroma.query_documents(namespace, claim, n_results=3)
2. If results is empty: return "NO_RAG"
3. best = min(results, key=lambda r: r["distance"])  # lower distance = more similar
4. cosine_similarity = 1 - best["distance"]  (ChromaDB returns L2 or cosine distances)
5. If cosine_similarity < 0.80: return "UNVERIFIED"  (no strong match found)
6. Run entailment check — single LLM call:
   prompt = f"Does this source text support the claim?\nCLAIM: {claim}\nSOURCE: {best['document'][:400]}\nAnswer with JSON: {{'entails': true|false, 'reasoning': '...'}}"
   Parse the JSON response.
7. If entails == True: return "SUPPORTED"
8. If entails == False: return "UNSUPPORTED"  (evidence found but contradicts claim)
